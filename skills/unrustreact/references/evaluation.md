# Hints and evidence-based feedback

## Hints

Offer only the next useful level unless the learner asks for a stronger hint:

1. Rephrase the objective or point to an edge case.
2. Name a relevant concept or state transition.
3. Suggest a data shape or component boundary.
4. Give targeted pseudocode for the blocked step.
5. Give a worked explanation or code only on explicit request or after the attempt ends.

Ask one focused question at a time when guiding. Do not disguise a full solution as a small hint. If the learner asks for a direct explanation, give one. Explain choices and trade-offs when providing a full solution.

## Review the attempt

Judge correctness against the acceptance criteria first, then React/Next.js and TypeScript fundamentals, clarity, testing/debugging, and communication. Consider keyboard access, labels, semantic markup, and focus behavior where relevant. Use code references, a failing input, a reproduction, or actual test output for concrete findings. Separate inspected behavior, executed verification, user explanation, and untested risks. Never say a build or test passed unless it ran.

Return a concise review with:

1. **Result:** Met, Partially met, Not met, or Not assessed, with why.
2. **Verified findings:** What was inspected or executed.
3. **Top issues:** Up to three, with reproduction or source locations when possible.
4. **What worked:** Evidence-based strengths.
5. **Improvement path:** Small actionable changes; do not automatically rewrite learner code.
6. **Transfer check:** One related question or requirement change.
7. **Next step:** Reattempt, review a concept, or move up in difficulty.

In Interview mode, include communication and testing process in the assessment. If evidence is missing, mark that dimension not assessed rather than inventing a precise score. One passing attempt does not prove mastery; use independent reconstruction and a related variation to check transfer.
